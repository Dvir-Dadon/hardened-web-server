        What is in place

        Network & access

        • Host firewall (ufw): only 22, 80 and 443 are open
        • SSH keys only, direct root login disabled, admin through a non-root sudo user
        • SSH: MaxAuthTries 3, no X11, agent or TCP forwarding, verbose logging, legal banner
        • Fail2ban jails for SSH and for web scanners (nginx-botsearch)

        Web layer

        • TLS 1.2 / 1.3 only, Let's Encrypt per site with automatic renewal, HSTS
        • Strict Content-Security-Policy (no inline code) and security headers, set once for every site
        • Catch-all server: unknown names and bare-IP requests get no answer and no certificate
        • Hidden, backup and secret files blocked; server version hidden

        Operating system

        • Kernel and network hardening with sysctl
        • Unused kernel modules blocked (dccp, sctp, rds, tipc, usb-storage)
        • Core dumps disabled, compilers restricted to root
        • auditd, sysstat and process accounting running

        Operations

        • Automatic security updates, with a reboot at 02:00 UTC when a kernel update needs one
        • My security-check.sh: logins, failures, bans, scans, backdoor checks, updates
        • Live attack counts regenerated every 20 minutes, no IP addresses published or stored
        • Weekly manual review of this dashboard and the audit script output

        Incidents I investigated

        Incident 1 · False positive

        "Successful SSH logins" every hour

        Alert
        My log check reported a successful SSH login roughly every hour, which would mean the server was compromised.
        Investigation
        I read the matching raw log lines. They were not logins: the search for Accepted was also matching …not in PubkeyAcceptedAlgorithms, which sshd logs when it rejects a bot that offers an old ssh-rsa key.
        Fix
        I anchored the detection rule to the real login message (Accepted publickey|password for …) and re-checked: no unknown logins.
        Lesson
        Validate a detection rule against the raw events before trusting it. A loose rule creates alert fatigue, or hides a real alert.

        Incident 2 · Suspected timestomping

        A file dated in the future

        Alert
        A file on the server showed a modification time in the future, a classic sign of timestomping (MITRE ATT&CK T1070.006).
        Investigation
        I compared the timestamps with stat. The modification time (mtime) can be set by any program. The birth time and the change time (ctime) are set by the kernel: both were from September 2026, when I added the image. Only the mtime pointed to 2027.
        Root cause
        wget copies the server's Last-Modified header into the file's mtime by default. Benign.
        Lesson
        Know which timestamps an attacker can forge and which they can't, and find a benign explanation before you escalate.
